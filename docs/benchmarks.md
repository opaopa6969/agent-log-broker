# Engine Benchmarks

Performance baseline and optimisation log for the broker engine. Generated by
the LOOP ENGINEERING MODE run on 2026-08-16.

## How to run

```bash
npm run bench       # vitest --bench (tinybench backend)
npm test            # unit tests (73 tests)
npm run typecheck   # tsc --noEmit
```

The benchmark suite lives at `tests/broker/broker.bench.ts` and covers the
four hot paths the engine spends its time in:

1. `RedactionPipeline.process()` — content-aware work per log line
2. `SubscriptionManager.matches()` — filter evaluation per (event, sub)
3. `BrokerCore.distribute()` — fan-out dispatch per event
4. `FileWatcher.readNewLines()` — JSONL tail read per change notification

A fifth composite bench manually wires `redact → match → distribute` to
measure the end-to-end cost the orchestrator will incur once it is
implemented (today the components are not wired; `BrokerCore.distribute` is
still a stub that does not call redaction or `matches`).

percentile estimates.

### FileWatcher measurement correction

The first baseline reported FileWatcher at ~240 Hz (4.2 ms per 1000-line
read). A microbenchmark showed the real per-call cost was ~1 ms, not ~4 ms.
The bench was creating a temp directory and writing 1000 lines *inside* the
timed function, attributing all I/O cost to `readNewLines`. Moving setup to
`beforeAll` produced the corrected figure:

| Bench | Before correction | After correction | Ratio |
|---|---|---|---|
| initial read — 1000 lines | 240 Hz | 34,239 Hz | 142x (measurement fix) |
| incremental read — 10 lines | 190 Hz | 25,791 Hz | 135x (measurement fix) |

This is **not** a code optimisation — the FileWatcher implementation is
unchanged. The original number was a measurement artefact. The corrected
figure (~34 kHz, ~0.03 ms/call) shows FileWatcher is not the bottleneck.

## Optimisation: RedactionPipeline single-pass replace

The original `RedactionPipeline.process()` scanned each regex twice:

```ts
const matches = redactedText.match(pattern);   // scan 1: count
if (matches) {
  redactionCount += matches.length;
  securityFlags.push(/* ... */);
  redactedText = redactedText.replace(pattern, replacement);  // scan 2: redact
}
```

The optimised version scans once using `replace` with a counting callback:

```ts
let count = 0;
redactedText = redactedText.replace(pattern, () => {
  count++;
  return replacement;
});
if (count > 0) {
  redactionCount += count;
  securityFlags.push(/* ... */);
}
```

This also removes a latent bug: the original reused the same `/g` regex
object for `match` and `replace`, relying on `lastIndex` being reset between
calls. The single-pass form never has to reason about `lastIndex` state.

### Correctness verification

All 73 existing tests pass unchanged. A direct equality check on all three
redaction levels confirms the new implementation produces byte-identical
`redactedText`, the same `redactionCount`, and the same number of
`securityFlags` for every input.

### Measured improvement

Run-to-run jitter in `vitest bench` is ±10-30% on this hardware, so the
headline numbers are from an interleaved microbenchmark that alternates the
two implementations within a single process to cancel out scheduler noise
(50,000 iterations per measurement, 5 rounds, order reversed each round).

| Redaction level | Before (μs/op) | After (μs/op) | Speedup |
|---|---|---|---|
| minimal | 5.71 | 3.13 | **+83%** |
| standard | 7.44 | 3.66 | **+103%** (2x) |
| strict | 7.11 | 4.85 | **+47%** |

The `standard` level gets the largest win because it scans both PII and
credential patterns, so eliminating the double-scan pays back on every
pattern. `strict` wins less because the additional file-path work it would
do is not yet implemented (the level is wired but has no extra patterns
today, so it behaves like `standard` plus an empty pass).

### Positioning

- **Redaction** (~225-256 kHz before, ~400 kHz after) — comparable to pino's
  optimised logger (~140 kHz) and well above Winston/Bunyan (~26-37 kHz). The
  RedactionPipeline does string scan + mask only (no fd.write), so being
  faster than a full logger is expected.
- **Subscription matches** (20 MHz full_stream, 800 kHz role mismatch) — no
  direct external comparator; these are pure predicate evaluations. The
  full_stream path at ~50 ns/op is near the limit of V8's inline caches.
- **distribute** (40 kHz for 20 consumers) — roughly Filebeat-class
  (~27k events/s) and half of FluentD (~91k). Single-process Node.js, so
  multi-process/worker_threads could reach Vector-class (~268k). The stub
  delivery returns synchronously; real HTTP POST will dominate this cost.
- **FileWatcher** (~34 kHz) — 1000 lines in 0.03 ms. This is the
  corrected figure; the original 240 Hz was a measurement artefact.

## What was NOT changed

- `BrokerCore.distribute` remains a stub. Real HTTP POST delivery is the
  next largest lever but is out of scope for this benchmarking pass.
- `SubscriptionManager.matches` role-mismatch path is 27x slower than
  `full_stream` (800 kHz vs 20 MHz) but still sub-microsecond. Optimising
  it further (e.g. `Set` instead of `Array.includes`) would shave nanoseconds
  for no practical gain at current traffic levels.
- `FileWatcher` is already fast enough (~34 kHz). The 240 Hz figure was a
  measurement bug, not a code bug.
- Pipeline wiring (orchestrator connecting watch → parse → redact → flag →
  match → distribute) is still unimplemented. The composite bench simulates
  it to give a baseline for when it lands.
